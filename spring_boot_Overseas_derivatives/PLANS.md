# 패키지 리팩터링 계획

## 목표
- 백엔드 패키지를 도메인별 책임 기준으로 재구성한다.
- 기존 동작을 유지하고, 사용자 작업과 무관한 변경은 건드리지 않는다.
- 리팩터링 이후 백엔드 빌드와 테스트가 정상 동작하는지 검증한다.

## 범위
- 대상: `backend/src/main/java/com/derivops/mvp`
- 중점: 컨트롤러, 서비스, 엔티티, 리포지토리, DTO가 한 디렉터리에 섞여 있는 도메인 패키지 정리
- 제외: 기능 변경, UI 개편, 관련 없는 워크스페이스 정리

## 목표 구조
- `api`: 컨트롤러
- `application`: 서비스 및 유스케이스 오케스트레이션
- `domain`: 엔티티, 열거형, 핵심 모델
- `dto`: 요청/응답 모델
- `infrastructure`: 리포지토리와 구현체
- `common`: 공통 예외, 보안, Query 유틸리티

## 수행 단계
1. 작업 계획과 체크리스트 문서를 추가한다.
2. 백엔드 클래스를 도메인 내부 역할별 하위 패키지로 이동한다.
3. 운영 코드와 테스트 코드의 패키지 선언 및 import를 갱신한다.
4. 백엔드 빌드와 테스트로 스캔 누락 및 import 오류를 확인한다.
5. 완료 상태를 `task.md`에 기록한다.

## 위험 요소
- 대규모 패키지 이동 시 Spring 컴포넌트 스캔이 깨질 수 있다.
- JPA 엔티티와 리포지토리 이동 시 Querydsl 생성 코드와 충돌할 수 있다.
- 이미 변경된 작업 트리가 있으므로, 필요한 파일만 최소 범위로 수정해야 한다.

## AuditLog 비동기 이벤트 처리 계획

### 목표
- `AuditLogService`가 직접 저장하지 않고 감사 이벤트를 발행하도록 변경한다.
- 필터/요청 스레드가 감사 로그 insert에 블로킹되지 않도록 비동기 처리한다.
- 트랜잭션이 있는 경우 커밋 이후에 처리하고, 필터 같은 비트랜잭션 호출도 지원한다.

### 범위
- 대상: 백엔드 감사 도메인, 비동기 설정, 스모크 테스트
- 포함: 감사 이벤트 모델, 이벤트 발행 흐름, `@Async` 리스너/executor, eventual consistency 테스트 보강, 작업 추적 동기화
- 제외: 감사 조회 모델 변경, 프론트 변경, 보안 정책 변경

### 수행 단계
1. 현재 `AuditLogService` 저장 경로와 비동기 인프라 유무를 점검한다.
2. 감사 이벤트 발행과 fallback을 포함한 비동기 트랜잭션 이벤트 리스너를 추가한다.
3. 감사 전용 task executor를 추가하고 Spring async를 활성화한다.
4. 비동기 저장에 맞춰 테스트를 보강하고 백엔드 검증을 수행한다.

## Envers 적용 계획

### 목표
- JPA 도메인 엔티티에 Hibernate Envers를 적용해 변경 이력을 남긴다.
- 커스텀 감사 테이블인 `AuditLog` 엔티티는 Envers 대상에서 제외한다.
- 비밀번호 해시 이력이 revision 테이블에 저장되지 않도록 한다.

### 범위
- 대상: 백엔드 JPA 엔티티, 백엔드 빌드 파일, 스모크 테스트
- 포함: Envers 의존성, 엔티티 애너테이션, `UserAccount.passwordHash` 제외, revision 테이블 검증
- 제외: revision 조회 API, 커스텀 revision 메타데이터/리스너, `AuditLog` 기능 제거

### 수행 단계
1. JPA 엔티티 범위를 점검하고 Envers 적용 대상을 확정한다.
2. Hibernate Envers 의존성을 추가하고 `AuditLog`를 제외한 엔티티에 애너테이션을 적용한다.
3. `UserAccount.passwordHash`를 Envers 이력에서 제외한다.
4. revision 테이블 생성과 `audit_logs_aud` 미생성을 테스트로 검증한다.

## 프론트 토큰 자동 갱신 계획

### 목표
- 프론트엔드에서 access token 만료 시 자동으로 refresh token을 사용해 세션을 연장한다.
- refresh token이 일반 API 인증 토큰으로 사용되지 않도록 백엔드에서 구분한다.
- 인증 실패 시에는 저장된 인증 정보를 정리하고 로그인 화면으로 복귀할 수 있게 한다.

### 범위
- 대상: 백엔드 인증 API/JWT 처리, 프론트 인증 저장소와 API 클라이언트, 스모크 테스트
- 포함: refresh token 발급/갱신 API, access/refresh 토큰 분리, 프론트 자동 재발급 및 재시도, 테스트 보강
- 제외: DB 기반 refresh token 저장소, httpOnly cookie 전환, SSO 연동

### 수행 단계
1. 현재 로그인 응답과 프론트 인증 저장 구조를 점검한다.
2. 백엔드에 refresh token 발급/재발급 API와 JWT 타입 검증을 추가한다.
3. 프론트 요청 레이어에 만료 임박 선제 갱신과 401 재시도 로직을 추가한다.
4. 인증 스모크 테스트를 보강하고 백엔드/프론트 빌드를 검증한다.

## 메뉴 N Depth 구조 계획

### 목표
- 메뉴를 부모-자식 관계 기반으로 관리해 2 depth를 넘는 계층도 표현할 수 있게 한다.
- 사용자용 사이드바는 트리 구조로 렌더링하고, 관리 화면에서는 부모 메뉴와 깊이를 확인할 수 있게 한다.
- 기존 메뉴 권한 필터링과 시드 데이터는 유지하면서 계층형 구조로 자연스럽게 전환한다.

### 범위
- 대상: 백엔드 메뉴 엔티티/서비스/시드, 프론트 사이드바/메뉴 관리 화면, 메뉴 관련 테스트
- 포함: 부모 메뉴 키 저장, 트리 응답 구성, 계층형 시드 데이터, 관리 화면 depth 노출
- 제외: 메뉴 CRUD API 신설, 권한 체계 재설계, 다른 도메인 화면 개편

### 수행 단계
1. 현재 메뉴 엔티티와 응답 모델에 부모/깊이 표현이 가능한지 점검한다.
2. 메뉴 엔티티와 시드 로직에 부모 메뉴 키를 추가하고 기존 데이터를 계층형으로 재배치한다.
3. `/menus/my` 응답을 트리 구조로 변환하고 관리 목록은 부모 메뉴/깊이를 함께 노출한다.
4. 프론트 사이드바를 재귀 렌더링 구조로 변경하고, 접힌 상태에서도 접근 가능하도록 보완한다.
5. 백엔드 테스트와 프론트 빌드로 구조 변경이 깨지지 않는지 검증한다.

### 위험 요소
- 부모 메뉴 권한이 자식 메뉴와 어긋나면 특정 역할에서 메뉴가 사라질 수 있다.
- 계층형 구조로 바뀌면 접힌 사이드바에서 하위 메뉴 접근성이 떨어질 수 있다.
- 기존 평면 정렬 기준만으로는 관리 화면에서 계층 순서가 직관적이지 않을 수 있다.

## 부팅 복구 및 E2E 검증 계획

### 목표
- 메뉴 2 depth 정리 이후 깨진 서버 부팅을 복구한다.
- 백엔드는 실제 기동과 주요 API 흐름으로 확인하고, 프론트는 브라우저 시나리오로 E2E 수준 검증을 수행한다.

### 범위
- 대상: 메뉴 초기화 로직, 서버 기동 경로, 프론트 로그인/주요 화면 진입 흐름
- 포함: 부팅 오류 수정, 백엔드 실행 확인, 브라우저 기반 프론트 검증
- 제외: 새 E2E 프레임워크 도입, 테스트 파일 대량 추가

### 수행 단계
1. 메뉴 정리 로직으로 인해 발생한 부팅 오류를 수정한다.
2. 백엔드 부팅과 스모크 테스트를 다시 확인한다.
3. 프론트/백엔드를 함께 띄운 뒤 브라우저로 로그인과 핵심 진입 흐름을 검증한다.
4. 결과와 잔여 이슈를 정리한다.
